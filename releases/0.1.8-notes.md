# Plebian-OS 0.1.8

Prepared 2026-08-07; published 2026-08-09.

Plebian-OS 0.1.8 is the coordinated stack release after 0.1.7, and the first
one that must upgrade an installed machine in place rather than being installed
fresh. It combines Plebian-OS, Pleb, Kilix, and Kilix 95 over the same pinned
Debian installer, package snapshot, terminal engine, Go toolchain, optional
desktop closure, and offline voice closure that 0.1.7 pinned, with the
component refs moved to this cycle's reviewed commits.

## Publication status

The four coordinated `v0.1.8` tags and the
[Plebian-OS 0.1.8 release](https://github.com/itsmygithubacct/plebian-os/releases/tag/v0.1.8)
were published on 2026-08-09. The release assets carry the strict ISO, checksums,
source and build provenance, and acceptance record. Those immutable artifacts
and their published checksums are authoritative for artifact identity; this
branch copy records the publication status after the release tag was created.
This source file by itself is not an artifact acceptance record.

Publication followed the strict ISO, BIOS, UEFI, installed-VM, catalog, voice,
provenance, and reboot procedure in [`RELEASING.md`](../RELEASING.md), plus the
six-gate in-place upgrade run in [`UPGRADING.md`](../UPGRADING.md).
Any earlier local candidate ISO produced while 0.1.8 was in development
predates the published closure and is not release provenance.

## Install and upgrade policy

0.1.8 upgrades in place from **0.1.7**, the immediately previous published
release, preserving user files, application and game state, provider/desktop
state, shared settings, operator session choices, and custom wallpaper/layout.

No skip from an earlier release is supported: 0.1.2 to 0.1.8 is a fresh
install, and 0.1.7 remains the fresh-install baseline for anything older. The
six upgrade gates in [`UPGRADING.md`](../UPGRADING.md) must be completed against
a real 0.1.7 installation created from the published 0.1.7 image, using the path
documented for installed users rather than a developer checkout. The section
below is reserved for that record, and a failed or missing upgrade run blocks
publication.

### Selecting the 0.1.8 closure

0.1.8 is the first release that has to ship the closure-selection mechanism
[`UPGRADING.md`](../UPGRADING.md) requires, because `plebian-os-update`
deliberately revalidates the release a machine already has and never selects a
new one. That mechanism is
[`provision/plebian-os-select-closure.sh`](../provision/plebian-os-select-closure.sh),
and it ships in this release, not in 0.1.7 — so a 0.1.7 machine fetches the
published `v0.1.8` tag and runs the selector out of it.

On the installed 0.1.7 machine, as the Pleb user (never through `sudo`):

```sh
SRC="$HOME/.local/gpu_terminal/sources/plebian-os"
SEL="$(mktemp)"
git -C "$SRC" fetch --force origin 'refs/tags/v0.1.8:refs/tags/v0.1.8'
git -C "$SRC" show v0.1.8:provision/plebian-os-select-closure.sh >"$SEL"
bash "$SEL" 0.1.8
```

That validates `releases/0.1.8.env` as read from the `v0.1.8` tag — every
coordinated ref, the Debian snapshot, the engine and Go pins, and the complete
Kilix Voice closure — reports each release-controlled key it moves, and swaps
them into `/etc/pleb/session.env` as one closure with a single rename, leaving
session, provider, storage, kiosk, appearance and layout choices untouched. It
saves the previous configuration under `/var/lib/plebian-os/closure-rollback.*`;
re-running the selector with `--rollback` puts it back. Add `--dry-run` to
validate and report without writing.

Only then, and with nothing privileged in between:

```sh
plebian-os-update --restart
```

Keep `$SEL` until the upgrade has succeeded — it is the only copy on the machine
until the updater moves the source checkout to the 0.1.8 commit — then
`rm -f "$SEL"`. Once the machine is on 0.1.8 the selector is present in that
checkout, so selecting the next release is one command:

```sh
~/.local/gpu_terminal/sources/plebian-os/provision/plebian-os-select-closure.sh 0.1.9
```

### Upgrade acceptance result

**PASSED.** All six gates were run in order on 2026-08-08, against the closure
this release ships, in a virtual machine installed fresh from the published
0.1.7 image. An earlier run against the *previous* 0.1.8 closure (pleb
`25d8cec`, kilix `df641fb`) also passed the six gates, but acceptance then
found a blocker in it: a mid-transaction failure which had rebuilt the engine
left `build/previous` naming a collected generation, and both update paths
refused the machine afterwards. That result was discarded rather than kept.
The record below is the re-run against the fixed pins, and it includes the case
that produced the blocker — a mid-transaction failure after a complete engine
rebuild — together with the regression check the earlier closure failed. No
skip path is claimed or supported for 0.1.8: upgrade from 0.1.7.

**Which gates ran against which commit.** The four component pins have not moved
since that run — Pleb `3878edc`, Kilix `85785f6`, Kilix 95 `dc185f1` and Kilix
Voice `eda9ca9` are the commits it tested, and `releases/0.1.8.env` is unchanged
— but Plebian-OS itself moved twice afterwards, for this acceptance record and
for the provisioner pin-integrity fix recorded below, so the release commit is
now `2f399e8`. **Gates 3 and 4 were re-run against `2f399e8`**, on the same
machine restored to its gate-2 sentinel state, because those two are the gates
that execute the target release's own code: the updater and OS layer it deploys,
the engine it rebuilds, and the closure selector read out of its tag. Gates 1,
2, 5 and 6 are carried from the run against `c7c907d`: gate 1 verifies the
*starting* 0.1.7 machine, gate 2 plants sentinels on it before anything is
updated, gate 5 compares the seven release-controlled keys the closure moves —
identical in both closures — and gate 6 is this record. A Plebian-OS-only change
that leaves every component pin where it was cannot invalidate any of them, and
the re-run gates re-proved what gates 2 and 5 cover anyway: the sentinel audit
taken before the re-run matched the gate-2 baseline byte for byte, and matched
it again after the induced failure, and every sentinel and shared setting was
byte-identical after the successful upgrade.

**Substitution used, and what removes it.** `v0.1.8` was not published when this
run was made, so the documented `git fetch … refs/tags/v0.1.8` fails with
`couldn't find remote ref refs/tags/v0.1.8`. The release commit is on `main`, so
it was fetched into the installed machine's own checkout and the tag created
there locally (`git tag -f v0.1.8 2f399e8cb2ba…`, which the machine confirmed is
an ancestor of `origin/main` and whose `VERSION` reads 0.1.8) and the selector
was run with `--offline`, leaving the checkout's own HEAD and working tree
untouched. Nothing else about gate 4 changes, and publishing the tag makes the
documented command work verbatim.

**Sentinels (gate 2)** were planted as thirteen files plus thirteen
configuration values, and captured as a deterministic audit before anything was
updated: a user document, a binary file and a dotfile config in the home
directory; a game save; Kilix 95 provider data and provider state; Pleb, Kilix
and Plebian-OS component state; a session transcript; a custom wallpaper image
with the Pleb desktop state rewritten to select it, and a desktop layout in the
Kilix 95 shell state; six operator values in `settings.conf` spanning
appearance, logging, audio and game availability plus one unknown key; and six
operator-owned values in `/etc/pleb/session.env` — four existing choices changed,
plus the kiosk respawn choice and an unknown operator key added.

**Induced mid-transaction failure (gate 3).** With the 0.1.8 closure selected,
the updater was failed at its `component-update` boundary — after the OS layer,
the Pleb checkout, `pleb install` and the whole component update, including a
complete engine rebuild (`fork rebuilt`), had already succeeded. This is the
case that produced the earlier closure's blocker. Rollback restored the four
checkouts to their 0.1.7 commits, the runtime generation, the `current` symlink
and the `fork-built-ref` stamp, the deployed OS layer, and every sentinel byte
for byte; `settings.conf` and all operator session values were untouched, and
the updater reported no recovery material it could not restore. A full audit
differed from the pre-failure capture only in the closure the operator had
selected, which the updater deliberately does not revert;
`plebian-os-select-closure --rollback` then restored `/etc/pleb/session.env`
byte for byte, making the audit byte-identical to the pre-failure capture in
every field, its `session.env` hash included.

**The engine-rollback regression, checked explicitly (gate 3).** After that
rollback the build directory holds a single generation, `current` points at it,
and there is no `previous` entry left behind — no pointer at a collected
generation. The machine was then still updatable by **both** supported paths:
`pleb update` and `plebian-os-update` each ran to completion and exited 0, with
no refusal of any kind, and a full audit afterwards was byte-identical to the
gate-2 baseline. This is the check the previous closure failed.

**Successful upgrade (gate 4).** From the restored 0.1.7 baseline, the closure
was selected with the mechanism documented above — 7 release-controlled keys
moved, 23 already matched, 3 build-only keys validated — followed by
`plebian-os-update --restart` and a reboot, with nothing privileged in between
and no developer checkout involved. After the reboot all five version commands
reported 0.1.8, the four checkouts sat at the pinned commits, the engine
rebuilt to a new generation stamped with the pinned submodule commit
`8fcdc63a`, with `previous` naming the retained 0.1.7 generation, which still
exists on disk; the Kilix Voice runtime moved to `eda9ca90` against the same
pinned library and model hashes, and `/usr/local/share/plebian-os/VERSION` read
0.1.8. The session came back with Kilix 95 in page 1 of the main Kilix instance
— page strip, status widgets, pane controls, 95 flavour — with the operator's
planted desktop data present, and the updater logged that it preserved the
existing Pleb desktop state including the custom wallpaper. Every sentinel was
byte-identical, and the data root and per-component roots were still
target-user-owned and `0700`. Running a live session afterwards rotated the
planted transcript into the ordinary `transcripts/recent/` store as a
zstd-compressed file, which decompresses to the planted bytes exactly: normal
session-log rotation, not an upgrade effect and not data loss.

**Pin discipline (gate 5).** `/etc/pleb/session.env` is the same length before
and after the upgrade — 107 lines each — and differs by exactly seven values,
every one of them release-controlled: `PLEBIAN_OS_VERSION`,
`PLEBIAN_OS_RELEASE`, `PLEBIAN_OS_REF`, `PLEB_REF`, `KILIX_REF`, `KILIX95_REF`,
`KILIX_VOICE_REF`. Classifying every changed line found no operator-owned line
among them. No session, provider, storage, kiosk, appearance, logging, thermal,
audio, network, game, wallpaper or layout value changed, in that file or in
`settings.conf`, whose content hash is unchanged from before the upgrade; the
unknown keys planted in both survived unchanged. The gate 3 and 4 re-run against
`2f399e8` reproduced that measurement exactly — 107 lines each side, fourteen
`diff` lines, seven release-controlled keys, no operator-owned line among them —
which is why this gate is carried rather than re-opened.

**The provisioner fix in this release commit, checked on the upgraded machine.**
`eaca706` is part of the release commit because a bare
`sudo plebian-os-provision` — the command `plebian-os-update` recommends for
OS-layer changes — used to reset nine values in `/etc/pleb/session.env` to
built-in defaults: the desktop provider selection, the five Kilix Voice media
pins, and the Go toolchain version with both architecture hashes. Run with no
explicit pins on the machine gate 4 had just upgraded, the provisioner exits 0,
reports the whole installed closure it restored from `/etc/pleb/session.env` and
the install policy it restored from `/etc/default/plebian-os`, and **every
release-controlled key, the desktop provider included, comes through
byte-identical**. The file as a whole does not: sha256 `0f6f228e…` becomes
`2038a3ba…` and 107 lines become 104. Everything that differs is
operator-owned. Three optional-desktop choices are reset to the
built-in default — `KILIX_CAP_AUTO_INSTALL`, `KILIX_TUI_UTILS_AUTO_INSTALL` and
`KILIX_LAND_DESKTOP_AUTO_INSTALL` each go `0` to `1` — and everything an
operator appended below the managed block is dropped, here a comment, a
`PLEB_RESPAWN=0` kiosk choice, and an unknown operator key. That is the same
shape of bug on the operator half of the file that `eaca706` fixed on the
release half. It fails no upgrade gate — no privileged provisioner runs during
an upgrade, and the updater preserved every one of those values across gates 3
and 4 — but it is a real defect in a command the updater recommends, and it is
recorded here rather than left to be rediscovered.

**Known divergence, recorded rather than claimed.** An in-place upgrade moves
the coordinated closure, not the Debian package set. The updater deploys 0.1.8's
dependency installer but never runs it, so an upgraded machine keeps the package
set and archive components its installed image shipped: `cmake` arrived because
`pleb install` requires it, but `nodejs`, `npm`, `ripgrep` and `kitty-terminfo`
did not, and Debian's `non-free` component stayed disabled — the archive keeps
`main contrib non-free-firmware` — so the optional mbrola read-aloud voice data
is still absent and read-aloud falls back to espeak-ng. `xterm-kitty` still
resolves, from the per-user terminfo
Kilix installs. None of this is release-controlled configuration and none of it
is covered by the six gates, but an upgraded 0.1.8 machine is not package-set
identical to a freshly installed one. Operators who want the added tooling can
run the deployed dependency installer after the upgrade has committed.

## Highlights

- **`kilix install`** — one list of everything this system can install: the
  pinned content catalog and the coding agents together, with their installed
  state, `--update`, and `--json`. The catalog half drives the desktop's own
  content module and the agent half runs each vendor's documented command,
  printing it and its documentation URL before asking to run it. The Kilix TUI
  desktop and the Kilix 95 Start menu both reach that same command rather than
  keeping catalogues of their own; Programs also gains a Coding Agents entry
  whose context menu reaches Claude Code, Codex and Kimi Code individually.
- **Host verbs for desktop parity** (SDK 1.7 → 1.9): `kilix games play`,
  `kilix launcher`, `kilix power`, `kilix update --stack`,
  `kilix security password-status`, `kilix laptop`, `kilix volume`, and
  `kilix default-desktop`. Every desktop provider was growing its own copy of
  these; they are declared once on the host, and the laptop's run registry
  means a session opened from one desktop is visible and closable from every
  other. `kilix_sdk.xdgapps` becomes the one authored freedesktop scanner.
- **An optional NVIDIA driver installer**, `plebian-os-nvidia-driver`, put on
  `PATH` by the provisioner and never run by it. The image stays on nouveau.
  It installs the Debian way and refuses hardware too old for any driver Debian
  still ships, rather than producing a machine whose X server will not start.
  Debian's `non-free` component is enabled by default so such packages are
  reachable; nothing from it is installed by default.
- **Prerequisites the stack was missing**: `nodejs`, `npm`, `ripgrep` for the
  coding agents, `cmake` for the CPU model runtime, and the `kitty-terminfo`
  package so `TERM=xterm-kitty` resolves from the system database.
- **A manual review of the released 0.1.7 image on two machines**, which is
  where most of this release's fixes came from: dictation refusing every
  ordinary shell prompt, `TERM=xterm-kitty` resolving nowhere, the voice
  tooling contradicting itself across doctor/daemon/installer, `~/.local/bin`
  reaching none of the stack's execution paths, coding agents reading as absent
  from where their own installers put them, two desktop games dying wordlessly,
  `plebian-os --version` crashing and then reporting the wrong checkout, and
  transcript labels clipped exactly where panes differ.
- **Update delivery**, which was where several of those fixes would otherwise
  have stopped: `pleb update` now moves the checkout Pleb itself runs from,
  component installers advance an existing checkout to a moved pin instead of
  reinstalling a stale tree, an installed Kilix Voice closure is refreshed, and
  every pinned move prints both ends and the file or variable that decided it —
  saying `DOWNGRADE` when it walks an installed component backwards.

## Provenance boundary

The exact resolved Plebian-OS commit, artifact hashes, generated package/source
manifests, fresh-install acceptance result, and the upgrade acceptance result
reserved above do not exist until the artifact is built and accepted. They must
be recorded from that build and attached with the ISO.

0.1.7 established the fresh-install baseline and had no supported upgrade
source. The published 0.1.2 artifacts have a separate forensic correction in
[`0.1.2-provenance.md`](0.1.2-provenance.md); its public tags were not moved and
its original assets were not replaced.
