## Workload

Each cycle runs a named-voice synthesis, a transcription, a voice clone, a
transcription, a voice design, a transcription, a cancellation (during model
load on odd cycles, during inference on even cycles), then a named-voice
synthesis and a transcription concurrently: 9 base jobs. Every 10th cycle adds
a deadline probe and a client-disconnect probe. After every job the runner
requires the provider to be ready with no active worker and no device grant
held or queued for that job.

## Memory

The runner recorded no memory figures. The host's own sysstat samples (every
10 minutes, 25 samples over the window) show memory in use between 0.55 and
5.0 GiB of 31.2 GiB as workers loaded and unloaded. The sampled peaks were
4.8 GiB in the first hour, 5.0 GiB at 00:30Z, and 4.5 and 4.4 GiB in the last
hour, so there was no upward trend. Available memory never fell below 21.6 GiB. These are host-wide samples, not
per-worker peaks. The soak account could not read the kernel log, so the
absence of OOM kills there was not checked; no job failed.

## Follow-ups

- The concurrent transcription waits for the synthesis job that holds the
  shared device lease. 13 of 132 transcriptions took over 115 s, and the slowest
  took 118.6 s against the 120 s budget. A slower or busier host would fail.
  Before relying on that budget, transcription should not queue behind
  synthesis, or the budget should account for the wait.
- Record per-worker peak memory in the runner for the next counted window.
- On this host, CPU synthesis is far slower than real time. The Qwen real-time
  requirement remains unmet. Do not advertise it.

The soak runner is test tooling outside product source. Before this window,
four runner defects were fixed:
- the clone prompt sent the WAV container instead of its PCM;
- the provider hello sent no arguments;
- the release-qualification check read fields the providers do not return;
- the device-grant check read keys no provider returns, so no run could have passed.
