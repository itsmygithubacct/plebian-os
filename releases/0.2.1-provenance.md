## Upgrade acceptance (C6) — PASS

0.1.9 -> 0.2.0 -> 0.2.1 on a VM installed from published 0.1.9 media, using the
documented operator procedure (selector extracted from the target tag, then
`plebian-os-update --restart`). Final state matches the commit table, with each
ref both pinned and checked out. Six preservation sentinels byte-identical; a
non-release-controlled `session.env` key survived while 29 release-controlled
keys moved.

Injected mid-transaction failure exercised deliberately: the machine remained
safe and usable, nothing was lost, and the documented recovery restored
coherence. The automatic rollback was partial under a persistent write fault --
recorded in `0.2.1-INDUCED-FAILURE-ROLLBACK-R1.md`, not papered over.

## Defects found during acceptance

All found by running the release rather than reading it. Recorded separately:

1. Recursive submodule fetch on an orphaned gitlink — blocked upgrades to 0.2.0
   AND 0.2.1. Remedied twice: object restored under an `archive/*` ref, and the
   fetch bounded in Pleb `6e1d3cc`.
2. The submodule-gitlink build gate itself reported healthy third-party
   repositories as broken (fetch-by-SHA is refused by default on GitHub). Fixed
   with a blobless-mirror fallback; both arms re-measured.
3. The uv installer ran unbounded, hanging first boot silently on a degraded
   link. Now bounded by `PLEBIAN_OS_UV_INSTALL_TIMEOUT`.
4. One untracked file in a source checkout blocks the whole-stack update, and
   this was undocumented on the documented upgrade path. Now documented.

Items 1 and 3 are in this artifact. Items 2 and 4 are in the build/docs and do
not change the installed system.

## Qualification: the artifact fails one check of its own acceptance gate

The installs recorded above were driven by hand. `build/acceptance-release-iso.sh`
validates the publishable bytes before booting them, and this artifact does not
pass it:

```
acceptance-release-iso: ISO build-info does not record manifest key
PLEBIAN_OS_NETINST_MAX_BYTES
```

Scope measured, not assumed: with only that key skipped in a throwaway copy of
the validator, the artifact passes the remaining **35 checks** and plans both
BIOS and EFI lanes, exit 0. It is the single gap.

Cause: `remaster-iso.sh` records `NETINST_URL` and `NETINST_SHA256` but never
`NETINST_MAX_BYTES`. That key is declared in the 0.2.0 and 0.2.1 manifests and
not in 0.1.9, so **every release ISO since 0.2.0 carries this gap**. It is
provenance completeness — the artifact holds the constraint as a build input
without stating it in build-info — and affects nothing about the installed
system. The installs above are genuine; the same bytes installed and booted on
both firmware paths and upgraded a bare-metal machine.

This record must not be read as saying the artifact passes its own gate,
because it does not. Fixed on the development line in `f5b1b76`, deliberately
not in `v0.2.1`: correcting it changes the ISO, which would invalidate the
evidence above.

## The `v0.2.1` tag was force-moved

It was moved once, before any artifact was published from the earlier target —
that commit could not build media, because its own submodule-gitlink gate
false-positived on third-party repositories. The move was owner-authorised, and
`RELEASING.md`'s prohibition is on replacing a provenance error with a moved
public tag, which is not what happened here: no artifact existed under the old
target.

It still has a consequence worth stating plainly. **Anyone who fetched `v0.2.1`
before the move holds a different commit under the same name.** The online
selector path fetches with `--force` and is therefore safe. `--offline`
resolves the tag from the local object store with no remote comparison, so a
stale local tag selects the old closure silently — the version matches, the
selection succeeds, and the machine lands on bytes nobody intended.

The authoritative target is the one recorded above:
`83837599bf4a1f4eeb3338fbc448d908c909d1c9`. A checkout that has seen this tag
before should refresh it explicitly before selecting:

```sh
git -C "$SRC" fetch --force origin 'refs/tags/v0.2.1:refs/tags/v0.2.1'
```

Documented for operators in UPGRADING.md as well.

## Known limitation

No SSH server ships in the closure (`openssh-client` only). A freshly installed
machine has nothing listening on port 22; remote inspection requires installing
`openssh-server` from the pinned snapshot, or console access.
