**Fresh install.** The provisioner's root image-model step runs
`install-image-models.py --install-paradee-runtime --offline`
(provision/plebian-os-provision.sh:7841). The desktop user's step runs
`--kilix ... --offline` (line 7845), after `install-default-models.py --offline`
and `stage-command-model.py --offline`.

With `--offline`, these steps download nothing:

  archive.
- `install_paradee` and `install_spacy` raise on a missing archive.
- Demucs, page OCR, Whisper medium.en and the espeak-ng source print a message

- The Neuronte part of install-image-models.py is skipped.

The provisioner's own Neuronte step installs from the image's

This session's fixture probe ran `main(["--install-paradee-runtime",
"--offline"])` with no archives. It raised "the installation media did not
supply the Paradee model" with no download attempted.

**Online upgrade without the Paradee and en_core_web_sm archives.** The RC9
updater calls the root step with `--install-paradee-runtime --no-ollama-runtime`
(provision/plebian-os-update.sh:6358). It has its own Ollama step,
`install_ollama_runtime_update`, earlier in the transaction.

In `main()` (provision/install-image-models.py:1263-1269),
`install_paradee_runtime` runs first. The older-updater Ollama shim runs only
afterwards, and only when neither `--offline` nor `--no-ollama-runtime` is
given. There is no Neuronte part in `--install-paradee-runtime`. The Neuronte
fallback (line 1308) runs at the end of the desktop user's mode, after Paradee
and en_core_web_sm.

This session drove the real RC9 `main()` and `install_paradee_runtime` against
fixture paths. Only the network was replaced: `urlopen` served the real pinned
Paradee ONNX, Paradee config.json, en_core_web_sm 3.8.0 wheel and espeak-ng
1.52.0 source. This session had downloaded those files from their pinned URLs
and checked each against its pin. The results:

- Correct bytes, run as an RC8 updater runs it (no flag), with the Ollama shim

  fetched, and only then did the Ollama shim run. The step raised the Ollama

- Correct bytes with `--no-ollama-runtime`: the same placement, exit 0, and the

- One flipped byte in the Paradee ONNX: "Paradee input size or checksum

- One flipped byte in the en_core_web_sm wheel: nothing placed. The Paradee
  archive was built but not placed, and the shim then ran.
- No network: nothing placed.
- Wheels needed and the first wheel download short: "incomplete download", and

`_place_shared_archive` verifies the staged copy before it links it into place.

test_delivery_statement_is_true_of_this_image (AC-8) passed against the RC9

Across the plebian-os diff from RC8, the provisioner, the updater, the closure
selector, install-deps.sh, install-neuronte.py and install-zell-runtime.py
change no line that names a voice model, the carrier, kilix-voice,

  before the model steps;
- `--no-ollama-runtime` on the root image-model step;
- install_neuronte_update, after the image-model step.

How this session reads one edge of the brief's claim: on an RC8 to RC9 update,
which runs the RC8 updater, an Ollama install failure inside the RC9 root step
happens after the Paradee and en_core_web_sm root work has finished and been
checked. A download failure is different: it is reported and the update
continues. The install failure makes the step exit non-zero. The RC8 updater
then reports "required Paradee runtime staging failed" and rolls the update
back before its desktop user's step installs Paradee and en_core_web_sm. The
next update tries again.

This neither skips that work nor places unchecked bytes, and the RC9 updater
treats the same Ollama condition as fatal at its own step. So this session does
not count it as breaking the gate. It does mean that the claim "cannot fail the
Paradee work" holds for the work itself and not for the exit status of that
invocation. The RC8 message misnames the cause, although the Ollama error is
printed above it.
