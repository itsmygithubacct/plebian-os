## Found during 0.2.3 release acceptance

- A first standalone closure selection is refused. Preparing the 0.2.2 standalone
  guest for the 0.2.2 -> 0.2.3 upgrade lane, `pleb update --to 0.2.2` failed with
  "could not select the split closure (status 6)". The selector's apply step reads
  `PLEBIAN_OS_VERSION` and `PLEBIAN_OS_RELEASE_MODE` from the saved session.env as
  its rollback record (`record_release_value ... || exit 6`), and a machine that has
  never selected a closure has neither value. A missing session.env fails the same
  way. With the owner's approval the two values were appended to the guest's
  session.env by hand, and the selection then completed. In 0.2.3 the function
  still refuses a missing value (its one change accepts a four-part version), so a
  first standalone selection is expected to fail the same way. The upgrade lane
  does not exercise it, because a machine selected once keeps the record in
  closure.env.
- kitty-pty-broker's reaping fix (`a5a5f2d3`) has no regression test for many
  adopted descendants exiting at once. Its review found that a broker reaping one
  child per loop iteration passes every suite, yet leaves 10 to 30 of 64
  simultaneously exiting orphans as zombies while the session is idle. The shipped
  loop reaps until nothing more has exited. Add a test whose orphans exit together.

## RC7 no-loop chat model

The owner approved `qwen-0.8b-no-loop-02` on 2026-11-09 as an optional
kilix-llm model for Kilix Avatar and LLM Chat, its Apache-2.0 and CC BY 4.0
licence record, standard-policy installation, kilix-llm installation during
provisioning, and thinking on for the LLM Chat entry. The model release is
published. RC6 was tagged without it, so it is rebased onto the RC6 pins as
the RC7 candidate.

The component commits are on GitHub (branch `work/0.2.3-rc7-no-loop`;
kilix-llm, its lab commit and kilix-avatar as before, kilix-avatar's
repository being private). Two independent seats reviewed carrier `42b6956b`
and the model's licence delivery; both returned "ship with known issues".
Their known issues:

- `kilix-llm pull --model-id qwen-0.8b-no-loop-02` fetches the GGUF into
  kilix-llm's own model path without the five notices or a licence receipt.
  The release publishes the licences beside the file and the GGUF metadata
  names Apache-2.0 and the CC BY edit, so the seat did not judge it a licence
  breach, but it is a second route that skips the wizard's notice delivery.
  Kilix 95's entries open only the wizard-installed file. Fix in kilix-llm:
  have `pull` install the notices too, or refuse this id and point at the
  model wizard.
- The kilix-avatar commit `a383f65a` could not be reviewed: its repository is
  private, as RC6's `bedd1b89` was. A seat with access should review it.
- A stale comment in kilix-content `tools/generate_upstream_records.py` says
  the owner has not signed off the CC BY component; the determination records
  the owner's approval and the generated rows are affirmative. Fix it in the
  next kilix-content commit.

The first candidate (`c889cb42`, kilix-llm `b26cadcd`) built kilix-llm's CPU
runtime during provisioning. It passed fresh-install acceptance (57 of 57
checks) and an RC6 upgrade. But on a 2 vCPU guest the step took 10 min 48 s:
5 min 24 s cloning llama.cpp's full history and 5 min 6 s compiling. It left
about 1.5 GB on every machine and lowered the catalog check's EnCodec
low-water mark at 24 GiB from 4.86 GB to 3.30 GB. On 2026-11-09 the owner chose
to build on first use and to slim the build:

- kilix-llm `ba4eaca3`: the first `run`, `chat` or `serve` builds the runtime
  when it is not built for the pin (a stamp in `bin/`, and a lock so concurrent
  first uses compile once). A finished build keeps only `bin/`, about 25 MB in
  place of 0.7 GB.
- kilix-avatar `c06f6aec`: runs `kilix-llm build --if-needed` before `serve`,
  with its own one-hour limit and a first-use status line, so serve's 300 s
  limit covers only loading.
- Kilix `55d7ea2a`: pins both and fetches only the pinned llama.cpp commit,
  about 50 MB of git objects in place of 483 MB. Kilix 95 `a9f28965` pairs
  with it; its entries are unchanged.
- Provisioning and upgrades install the launcher and source only.

These commits came after the seats' review, which read kilix-llm `b26cadcd`,
Kilix `58c36b2e` and Kilix 95 `24130253`. They change how kilix-llm is built.
They do not change what carrier `42b6956b` binds (it regenerates unchanged),
the model's licence delivery, or the entries. The first LLM Chat or Avatar
start with the model now waits for the CPU build.

The owner also had RC7 move the Kilix engine's Go from go.dev go1.27.0 to
go1.27.3 (2026-11-09), keeping the go.dev archive and its pinned hashes, and
moving to Debian's trixie-backports Go (`golang-1.27` 1.27.3-1~bpo13+1) after
0.2.3. Both go.dev hashes were checked against downloaded archives.

What remains:

- Fresh-install and RC6-upgrade acceptance of this candidate. In an RC6
  upgrade to `6a0e35db` (2 vCPU guest, busy host), provisioning compiled
  nothing and left llama.cpp shallow; the first `kilix-llm build --if-needed`
  then took 6 min 56 s and added 23 MB, and a repeat returned in 0.2 s. uv
  still fetches its managed Python 3.12 on kilix-llm's first run.
- llama.cpp's build fetches its web UI from Hugging Face (`ggml-org/llama-ui`,
  falling back to the unpinned `latest` archive); offline it builds without
  the UI. In the first-use build above, the pinned UI version `b14` returned
  an HTTP error both times it was fetched, so the build embedded `latest`.
  LLM Chat and Avatar do not use the UI. kilix-llm should pin it or build
  with `-DLLAMA_USE_PREBUILT_UI=OFF`.
- In the first candidate's RC6 upgrade, Whisper medium.en's download stopped
  at 428255018 of 1527904330 bytes. kilix-content `fetch.py` (unchanged since
  RC6) reported it as `size-mismatch` ("upstream size differs from the pin").
  The pin matches Hugging Face, and the partial is kept for the next upgrade.
  An early end of stream should be reported as an interrupted download.
- Kilix Avatar is still installed on first use (`kilix avatar`), so its
  no-loop entry, like the existing Avatar entry, appears only after that.
- On CPU a thinking reply in LLM Chat can take minutes. Without thinking
  neither model looped in testing.
- An upgraded machine keeps go1.27.0 until its Kilix engine is rebuilt,
  because Pleb's update checks Go only in that rebuild. Its provenance record
  then shows the closure's go1.27.3 beside the installed `go version`. Pleb
  could reinstall Go when the closure's Go pin changes.
- Use Debian's trixie-backports Go (`golang-1.27`, 1.27.3-1~bpo13+1 on
  2026-11-09) in place of the go.dev archive after 0.2.3. That adds a
  backports apt source, which Plebian-OS does not have yet, and changes the Go
  pin from an archive hash to a Debian package version.
- RC7 branches from the `v0.2.3-rc6` tag, as RC6 branched from RC5's. When it
  is merged into main, keep main's 0.2.3 known-issue entries (`5f67ef5`: the
  20 GiB EnCodec converter space and the fresh-install Waydroid helper).
